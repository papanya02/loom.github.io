Design

Architecture

Clear module boundaries. Identity, crypto, capabilities, path and transport are separated so future work can land behind stable APIs.

Module map

Runtime workflow and the pieces it owns.

Applications │ NEXUS Runtime (node.rs) ├── Identity (identity.rs) ├── Secure sessions (crypto.rs → snow) ├── Capability negot. (capability.rs) ├── Path policy (path.rs) ├── Transport adapters (transport.rs · TCP) └── Wire envelopes (wire.rs)

Trust & identity

Stable identity is an Ed25519 root. A separate Noise X25519 key protects the session.

ID

Peer ID

Derived from the root public key. Stable across Noise key rotation.

nx2 + hex(BLAKE3("NEXUS-Peer-ID-v2" ‖ root_pk))
✓

Certificate

Root signs a domain-separated binding of the Noise static key. Sent only after the channel is encrypted.

"NEXUS-NOISE-KEY-CERT-v1" ‖ root_pk ‖ noise_static_pk
OK

Verification

Noise finished → cert key matches handshake static → signature valid → Peer ID matches the local pin.

Pin-based trust. No global directory. No automatic web of trust.

Path planning

Applications choose an intent. The planner scores candidates.

Intents

balanced · low-latency · privacy-preferred · reliable

Today

Only the TCP candidate exists, so every intent still selects TCP. The API is the seam for future transports.

Non-goals

Explicitly out of scope for this prototype.

  • DHT or peer discovery
  • Routing between third-party peers
  • NAT traversal or relays
  • QUIC / UDP adapters
  • Offline delivery / store-and-forward
  • Multi-stream multiplexing
  • Session migration or resumption
  • Global trust / reputation system
